# AGENTS.md (scoped rules)

One rule per entry with a one-line why. Moved from the root AGENTS.md.

Edge Function rules live in `supabase/functions/AGENTS.md` (shared helpers in `supabase/functions/_shared/AGENTS.md`); homework and event SQL lifecycle rules live in `supabase/migrations/AGENTS.md`.

## Answers & Evaluation

- Internal configuration, newsletter and DSLM audit tables retain service-only policies and explicit service grants; `consume_newsletter_rate_limit` is service-only and client RPC grants are changed only through an exact audited allowlist, because blanket definer revocation breaks authorized teacher and share-token workflows.

- New event ratings are normalized by `normalize_dslm_ratings` at the `student_events` boundary; knowledge classification updates the original observation and flashcards also emit word-level ratings, without changing card scoring or historical events, because every evidence source must reach metrics without invented scores or duplicate observations.

- All worksheet text answer checking goes through `src/lib/answers/matchAnswer.ts`; an uncertain match (one that cannot be proven wrong) returns `review`, never `wrong`, and only these cases are provably wrong: an error-correction answer that copies the source sentence (unless the key says no error), and in grammar items (`grammar: true`: gap-text, fill-in-blanks, complete-word) a difference that is only a regular ending (s, es, ed, d, ing, ly, er, est, ies) on a stem of 3+ letters whose ending does not repeat the last stem letter; typos, transpositions, word order and vocabulary items stay `review` (Welcome Test grammar fill_blank items are compared strictly in `supabase/functions/_shared/welcomeTestKeyedAnswer.ts`, because the word form is what they test) — because false negatives destroy learner trust and DSLM accuracy, while unscorable inert items stop giving the negative signal they exist to measure.
- Every DSLM pipeline SQL function and trigger (answer -> event triggers, metric engine, answer RPCs, AI queue RPCs) is defined in `supabase/migrations/`, never only in the dashboard (enforced by `src/lib/__tests__/dslmSqlBaseline.test.ts`) — because the engine existed only in production and could not be reviewed.
- A DSLM event's weight in `compute_skill_metric` comes only from `public.dslm_event_weight` (version 1: homework submitted 1.0, homework draft 0.8, other sources 1.0; `docs/ux/learning-model-spec.md` §14), and `submit_homework_answers` flips `event_payload.is_submitted` of the submitted exercises — because the answer trigger ignores a submit-only change, so the draft flag stayed false for exercises the AI never re-evaluated.
- A DSLM migration is applied to production together with the code that calls it, and `pg_proc` / `pg_constraint` are checked afterwards; production SQL changes avoid `DROP` (use `CREATE OR REPLACE`, including triggers) because the SQL tool waits for a manual confirmation and times out; a function whose new argument would leave two overloads (PostgREST cannot choose) is replaced in its own migration file run in the SQL Editor (`save_mark_done_evaluation` and optional `p_prior_verdict`, `20261027090200`, order in `docs/operational/iteration-10-rollout.md`), the validation loop (`dslm_interpretation_params` version 1 seeded from code and parity-tested in `dslmParamsParity.test.ts`, `dslm_decision_log` written only through `log_dslm_decision`, `param_version` columns) is additive and never read by `compute_skill_metric` - because 20261015090300-090500 stayed unapplied while the deployed function called them, and compute_skill_metric v3 shipped without the constraint it needed, rolling back every new rated event.
- `public.worksheets.prompt` / `ip_address` and `public.homework_assignments.prompt` are not readable by anon/authenticated (table-level SELECT revoked, column-level GRANT SELECT in `20261028121000` and `20261029090000`; legacy homework engine system messages are blanked after the `scripts/dslm/backup-homework-prompt-before-hide.sql` backup and the client writes `prompt: null`); a new column on either table needs its own `GRANT SELECT (col) ON public.<table> TO anon, authenticated` plus an entry in `OWNER_VIEW_COLUMNS` (`src/lib/worksheet/worksheetColumns.ts`) or `HOMEWORK_OWNER_VIEW_COLUMNS` (`src/lib/homework/homeworkColumns.ts`), each compared with its migration grant list by its test, and client code never uses `select('*')` or a bare `.select()` on them — because an ungranted column fails every owner query with 42501 and the system prompt is core IP.

- `add_student_event` accepts only the student's own teacher (or the service role); SQL wrappers that authorise their caller themselves call `add_student_event_internal`, which no client role may execute (`20261014090000`) — because SECURITY DEFINER bypassed the RLS teacher check and any signed-in user could write events and skill metrics for another teacher's student.
- Student-facing pages (Welcome Test, homework) log DSLM events only through token/email-authorised RPCs (`log_welcome_test_event_by_share_token`, `log_homework_submitted_event`), never `add_student_event` or direct `student_events` writes — because those are teacher-only and anonymous calls fail silently with 401.
- The profile billing guard trigger tests `current_user = 'authenticated'`, never `auth.role()` — because the JWT role is still `authenticated` inside SECURITY DEFINER billing functions like `consume_token`, which then could not charge tokens.
