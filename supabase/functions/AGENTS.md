# AGENTS.md (scoped rules)

One rule per entry with a one-line why. Moved from `supabase/AGENTS.md` and `src/AGENTS.md`.

## Edge Functions

- `verify-open-answers` and `process-pending-ai-evaluations` accept only the service role, a signed-in user (worksheet owner for the queue) or a student proving access with share token + assigned email (`supabase/functions/_shared/evaluationAccess.ts`); the client reads and writes student answers only through the `*_by_share_token` RPCs via `src/lib/answers/studentAnswerRpc.ts` (owner teacher always passes; homework submit through `submit_homework_answers_by_share_token`, which also creates the teacher notification and the `homework_submitted` event; homework grading (`ai_evaluation`, `item_evaluations`, `mastery`, `eval_trigger`) is written only by the service role: the student page asks `process-pending-ai-evaluations` with `homework_id` + `trigger_source: 'submit_homework'` and `update_homework_answer_by_share_token` ignores student grading writes; the legacy id+email RPCs are revoked from anon and authenticated by `20261012200100` and `20261014090100` and stay callable only inside the SECURITY DEFINER wrappers and by the service role); `transcribe-audio` follows the same access rule and fetches only https audio from the allowlisted storage hosts with a 25 MB cap (`_shared/audioFetchGuard.ts`) — because the endpoints were a free public LLM proxy and answers were writable with an id and an email, or with the link token alone, and a link + email holder could rewrite a submitted homework and inject any skill at mastery 100.
- Student text sent to an evaluation model is wrapped with `wrapStudentText` under `STUDENT_TEXT_RULE`; only unambiguous grader-steering (`looksLikeInstructionInjection`: grader field names, or an override request plus a score request) is capped (`supabase/functions/_shared/promptSafety.ts`), never ordinary sentences — because a live probe scored a prompt-injection answer 1.0 while a broad filter would mark genuine answers wrong.
- Edge Functions build links from the `APP_BASE_URL` secret, never a hardcoded domain — because preview, published and custom domains differ.
- Scheduled Edge Functions (`pacing-periodic-check`, `loop-pacing-aggregator` and the other cron targets) require `x-cron-secret` or the service role key, never the anon key — because a cron job calling with the anon key made the endpoint public.
- Every AI model id used in `supabase/functions/**` is registered in `supabase/functions/_shared/modelRegistry.ts` (enforced by `src/lib/__tests__/modelAudit.test.ts`) — because `audit-llm-models` monitors and advises only on registered models.
- New non-protected Edge Function chat calls go through `executeAiCall(role, ...)` in `supabase/functions/_shared/aiGateway.ts`: the model id comes only from the `MODEL_REGISTRY` entry of that role (or its `AI_GATEWAY_MODEL_<ROLE>` override), with one registry `gatewayFallbackRole` attempt on 402/404/429/5xx/network errors and no retry of the same target; prompts are passed through unchanged and the Worksheet Generation Engine never uses it (tested by `src/lib/__tests__/aiGateway.test.ts`) - because scattered SDK clients and hardcoded ids made a provider switch a code change in every function.
- The AI evaluation queue is drained only through `claim_pending_ai_evaluations` (atomic, one row per worker step, stale-lock recovery, max 3 attempts including dead runs) and evaluates the answers stored in `worksheet_student_answers` at processing time; a scheduled call with `x-cron-secret` queues each saved answer at most once per save via `list_worksheet_answers_needing_ai_evaluation`, and retries stay with the claim; submitted homework answers are evaluated by the server right after submit (`processSubmittedHomework`, homework_id + share token) and, when that did not finish, by the same scheduled run through `list_homework_answers_needing_ai_evaluation` / `claim_homework_answer_ai_attempt` (max 3 attempts, never overwriting a finished row); `save_homework_answer` validates student ratings against the exercise's own skills, merges saves by key and takes the exercise type from the homework snapshot, and the ratings of submitted closed exercises are rebuilt by the server from the answers with `buildClosedItemEvaluations` (`_shared/closedRatings.ts`, parity-tested against the client builder; selection types are finalised in `finalizeClosedRows`, `eval_trigger` 'submit_homework' marks them done, and unsubmitted closed drafts are re-rated from the key by the scheduled run, marked '10min_inactivity') — because the ratings a browser sent for selection exercises were never checked and went straight into skill metrics, double processing, rows stuck in 'processing', no retries and evaluation that depended on an open browser tab lost or duplicated evaluations.
- `verify-open-answers` maps model results to answers by the echoed item id (`verify-open-answers/evaluationMapping.ts`); a missing, unparseable or non-numeric score leaves an open item unevaluated (never a made-up 0.7, never 25 in the Welcome Test); scores are read only by `parseModelScore` and a forced 0 for "no answer" only by `isNonAnswerText` (whole short answer) in `verify-open-answers/answerSignals.ts` — because positional mapping and fallback scores wrote fabricated values into DSLM, `parseFloat` turned an 85 into full marks and an unanchored "I don't know" pattern zeroed real answers.
- Welcome Test banks (`WELCOME_TEST_BANK_SIZES` in `_shared/welcomeTestBank.ts`) only grow by appending questions to `ALL_WELCOME_TEST_QUESTIONS`; display order and which adaptive questions a student sees come from `_shared/welcomeTestFlow.ts` (`visibleBranchIds`, `shownRows` on the server, `sectionsFor` in the browser), a bank 2 level comes only from `estimateLevelLadder` over `LEVEL_ITEM_CEFR` (bank 1 stays on `estimateLevel`), and `CURRENT_WELCOME_BANK` in `src/lib/welcomeTest/seed.ts` is raised to 2 only after the listening recordings exist — because a stored `question_index` must keep its meaning, a question never shown must not count as skipped or missed, and a transcript shown instead of audio would measure reading, not listening.

- `students.main_goal` is the tutor's goal and is written by `process-welcome-test` only when empty or "unknown" (never "custom"); `students.learning_track` and goal `kind`/`target_category` come only from the pure `_shared/goalTaxonomy.ts` (mirrored by the SQL backfill), a tutor/Welcome Test mismatch is only flagged as `metadata.conflict_status` on suggestions, and the track adds pacing only when `main_goal` matches no pacing keyword, because the Welcome Test used to overwrite tutor goals and a double-counted signal would skew pacing.
